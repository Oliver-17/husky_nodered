# husky_nodered

把 Low-Code 任務編排工具接到**第二種載具**：Clearpath Husky A200（地面無人載具）。
**只做模擬**，不涉及實體車輛。

這個套件存在的目的是驗證規格書 G-4／P-1 的主張：**換載具不用改 Node-RED、
不用改 `nodered_ros2`**。所以操作層、編排層、橋接層完全沿用無人機那一套，
只換掉決策層以下。

## 和無人機的差別（為什麼不是照抄）

| | 無人機 x500 | Husky A200 |
|---|---|---|
| 可控自由度 | 4（前後、左右、上下、機頭各自獨立） | 2（前進 v、轉向 ω） |
| 能不能側移 | 能 | **不能**，差速車，機頭就是移動方向 |
| 速度橋 | 需要 `cmd_vel_to_px4_node` | **不需要**，平台直接吃 `cmd_vel` |
| 起飛／降落／高度 | 有 | 沒有這些概念 |
| 終點朝向 | 不在乎（相機朝下） | 有意義（車頭） |

## 這個驗證證明了什麼、沒證明什麼

⚠️ 這一節是為了回答「**那不是換什麼車都一樣嗎？**」。這個問題問得對，
而且答案有一半是「是」—— 所以要先講清楚界線在哪，不要在口試台上被問倒。

### 證明了什麼（有證據，不是宣稱）

| 主張 | 證據 |
|---|---|
| 換載具不用改編排層 | `nodered_ros2` 改動 **0 行**（H4，git 歷史可查） |
| 兩種載具能共用同一個「等待完成」積木 | `task.seq`／`task.state` 協定一致，`test/t_status_contract.py` 綁著檢查 |
| 通用的介面其實很薄 | 無人機 8 個服務，地面車只要 3 個，同一套積木都接得起來 |
| 組合動作屬於編排層 | 「返航」兩台都是「導航到座標」＋`scene.home` 組出來的，決策層不提供 |
| 落差夠大才有說服力 | 可控自由度從 4 掉到 2、能側移 → 不能側移、有飛控 → 沒有飛控 |

### 沒證明什麼（四條，不要不小心講過頭）

1. **沒證明「任意載具」都行，只證明了「同一類運動學」。**
   換一台阿克曼轉向車（轎車）就不成立：有最小轉彎半徑、不能原地轉，
   `RotationShimController` 的整個前提（先原地轉對準路徑）直接失效，
   `NavfnPlanner` 規出來的路徑車子開不了，得換成 `SmacPlannerHybrid`。
   那是「換規劃器」等級的改動，不是調參數。
   **分界線是運動學類別，不是「車」或「飛機」。**

2. **沒證明定位問題解決了 —— 這裡是直接拿模擬真值。**
   Husky 模型身上**一個感測器都沒有**（沒光達、沒 IMU、沒相機、沒 GPS）。
   位置來自 `OdometryPublisher`，也就是 Gazebo 直接報模型在世界裡的實際位姿。
   輪式里程計有（DiffDrive 算的 `odom_wheel`），但因為滑移轉向灌水 46% 而
   不給 Nav2 用，而且這個專案沒有任何東西能把飄掉的 odom 拉回來。
   **「換什麼車都差不多」之所以成立，有一部分是因為載具之間最難的那塊
   （感知與定位）在這裡被整個拿掉了。**
   這一點和無人機是對等的（PX4 SITL 的 EKF2 在模擬裡也是吃真值），
   所以當成「兩台在同一個條件下比較」是公平的，但不等於實機可行。

3. **沒證明實機可行。** 要上實體 Husky，第 2 點那三個模擬捷徑
   （真值里程計、`map → odom` 是單位變換、區域 costmap 只有 `static_layer`）
   全部不成立，必須補上光達並換成 AMCL 或輪式＋IMU 的 EKF。
   這個套件第一行就寫了「只做模擬」。

4. **沒證明感知鏈能換載具。** 無人機那邊的 YOLO 追蹤整條沒有接到地面車，
   需求裡也沒有。所以 `drone_vision` 的 0 改動只代表「沒用到」，
   不代表「換載具不用改」。

### 口試用的一句話

> 我們把載具差異壓到決策層以下 —— 編排層和介面層一行都不用改，
> 代價是模擬裡用真值定位、而且只在同一類運動學之內成立。
> 要跨到阿克曼轉向或上實機，要改的是規劃器和定位，不是這套工具。

### 🔴 兩個會靜默失敗的地方（都已經修掉並留下測試）

**① 自己開的 Gazebo 不會算感測器。**
Gazebo 的 system plugin 清單在世界檔沒寫 `<plugin>` 時是從
`~/.gz/sim/8/server.config` 來的，那份**只有** Physics、UserCommands、
SceneBroadcaster，**沒有 Sensors**。PX4 開 Gazebo 時用的是它自己那份
（有 Sensors），所以「兩台同場」看不出問題，只有本套件自己開 Gazebo
（`husky_all`、`husky_sim`）時才會中。

症狀是**話題在、資料永遠是零**：`ros2 topic list` 看得到
`/husky/rgb/image`，但 `ros2 topic hz` 完全沒有輸出。沒有任何錯誤訊息。

解法：`gz/config/server.config`（本套件自己那份，多一個 Sensors），由
`husky_sim.launch.py` 設進 `GZ_SIM_SERVER_CONFIG_PATH`。
**不是**寫進世界檔 —— 世界檔和 PX4 共用，寫進去會讓 PX4 那條路載入兩次。

**② 權重要用 COCO，不是無人機的 VisDrone。**
VisDrone 是**空拍俯視**的資料集。地面車的相機水平朝前，看到的是車尾／車側，
完全不在那個分布裡。同一張倉庫影像（目標車在正前方 4 m）：

| 權重 | 結果 |
|---|---|
| `yolov8s-visdrone.pt` | conf 降到 **0.01 都完全偵測不到** |
| `yolo11s.pt`（COCO） | **0.876** |
| `yolo11m.pt`（COCO） | 0.877（沒有比 s 好，用 s 就夠） |

⚠️ 不要以為是信心門檻或尺度的問題去調參數 —— VisDrone 在這個視角是
「什麼都沒看到」，不是「看到但不夠有把握」。

⚠️ 也**不要用對比強的測試場景驗這件事**：在黑地板配亮車的簡易世界裡
VisDrone 反而測得到 0.83，會得到完全相反的結論。倉庫是灰車配灰地板，
那才是真的條件。

偵測器節點不用改：它是用**類別名稱**（`vehicle_classes` 參數，預設
`car,van,truck,bus`）去查該權重自己的 names 表，兩套權重都適用。
COCO 沒有 van，所以實際對到的是 car/bus/truck 三個。

**🔴 ③ 權重參數的名字一定要是 `husky_yolo_weights`（2026-11-15 踩到，藏了兩天）**

ROS 2 launch 的 `LaunchConfiguration` 是**跨 include 共用**的，而
`DeclareLaunchArgument` 只在「這個名字還沒有值」時才套用預設值。
`both_all` 先開無人機，`drone_nodered/launch/vision.launch.py` 宣告了
`yolo_weights = yolov8s-visdrone.pt`；輪到 `husky_vision.launch.py` 時那個名字
已經有值，它自己寫的 COCO 預設就**被安靜地忽略**了 —— 地面車實際跑的是
上面那張表裡「完全偵測不到」的 VisDrone。

症狀一點都不像設定錯：偵測得到，只是時有時無，看起來只像「視覺不穩」。
找出它的方法是**逐幀錄原始影像，再用同一顆權重離線重跑、逐幀比對**：

| | 偵測率 |
|---|---|
| 線上（實際載入 VisDrone） | 29% |
| 同一批影像，離線用 COCO | 60% |
| 線上漏掉、但離線看得到的 | 45% |

改名之後：看得到目標的時間 28% → **54%**，轉圈重找 31.6 → **3.4 秒**，
線上和離線的落差剩 **1%**。

判定法：`ros2 param get /husky/yolo_detector weights`，或看啟動日誌的
「載入權重 …」那一行。⚠️ 同一個陷阱還在 `debug_image`／`yolo_conf`／
`yolo_python` 上，只是兩邊預設值剛好一樣所以目前無害。

修完之後剩下的跟丟，**97% 是車根本不在畫面裡**（離線也偵測不到）：
被貨架擋住、靠太近（0.9 m 時橫向視野只剩 ±0.6 m）、或太遠（15 m 時框只有
12x8 px）。目標車是 0.6 × 0.32 × 0.235 m 的縮小模型，3 m 正後方只有約
45x35 px，本來就在小目標的邊界上。

### 目標的 map 座標（V1，2026-11-14）

`drone_vision/point_to_frame_node.py` 用 TF 把 `target_point` 換成 map 座標，
發在 `/husky/api/target`。那顆節點**沒有任何幾何計算**，純粹是 tf2 的轉換，
所以放在通用的 `drone_vision`，不綁任何載具。

⚠️ **不能**沿用無人機的 `target_world_node` —— 那是「射線和地面平面求交點」，
而地面車的相機幾乎水平。近乎平行的射線求交點，車身顛一下算出來的距離就從
5 m 跳到 50 m。地面車走深度，而深度點本來就是完整的 3D 點，只要換座標系。

TF 鏈（兩條靜態變換都在 `husky_vision.launch.py`）：

```
map → husky/odom → husky/base_link → husky/camera_link → husky/camera_optical
                                    └ 實體安裝 ┘        └ 標準光學旋轉 ┘
                                      (0.35, 0, 0.45)     yaw −90°、roll −90°
                                      俯角 10°
```

🔴 **`gz_frame_id` 一定要是 `husky/camera_optical`，不能叫 `camera_link`。**
`target_locator_node` 輸出的是**光學座標**（x 右、y 下、z 前），而 ROS 慣例裡
`camera_link` 是 x 前、y 左、z 上 —— 差一個 90°。取錯名字的話，任何拿 TF
換算的人都會把目標位置整個轉 90°，**而且不會報錯**。
（無人機沒中這個雷，是因為它根本沒用 TF。不要照抄它的命名。）

| 擺的位置 | `api/target` | x 差 | y 差 |
|---|---|---|---|
| (−12, 9) | (−12.274, 9.000) | −0.274 | +0.000 |
| (−11, 9) | (−11.278, 9.002) | −0.278 | +0.002 |
| (−9, 9) | (−9.280, 8.998) | −0.280 | −0.002 |
| (−6, 9) | (−6.286, 9.002) | −0.286 | +0.002 |

正前方時橫向誤差 **±0.002 m**，縱向固定偏近 **0.28 m**。
那 0.28 不是誤差 —— 深度量到的是**車尾表面**，而「擺的位置」是車體中心。
目標偏到一側時，這個偏移會沿著視線方向拆進 x 和 y（例如擺在 (−9, 8)
會得到 x −0.280、y +0.051），方向是對的。

⚠️ **z 會低約 0.14 m**。真值里程計發的 `odom` 把 z 歸零（`/husky/odom` 的
`position.z` 就是 0.0），所以 `husky/base_link` 在 map 的 z 是 0，而不是
模型原點真正的離地高度 0.14275。2D 導航用不到 z，但要讀 z 的話記得這件事。

### 🔴 rclpy + tf2 的陷阱（這次踩了兩個，症狀一模一樣）

兩個都會讓錯誤訊息變成
「`Lookup would require extrapolation into the future, latest data is at …`」，
看起來像時間戳對不上或 `use_sim_time` 沒設，**實際上是 TF 根本沒被收進 buffer**。

> **判定法**：另外寫一支只訂閱 `/tf` 的小程式量時間戳。如果 `/tf` 其實是即時的
> （實測只落後 clock 0.016 秒），而節點說「最新 TF 是 3 秒前」，那就是收不進來，
> 不是對不上。

**① 不要在訂閱回呼裡用會阻塞的 `timeout`，除非跑多執行緒執行器。**
`Buffer.transform(..., timeout=T)` 會卡著等 TF，而 TF 正是靠同一個單執行緒
執行器的 `/tf` 回呼灌進 buffer 的 —— 等於自己把自己餓死。15 Hz 的影像每幀
等 0.2 秒 = 每秒要等 3 秒，執行器直接飽和，實測 buffer 固定落後 3.3 秒、
**每一幀都失敗**。

解法是 `MultiThreadedExecutor` ＋ 把自己的回呼放在獨立的
`MutuallyExclusiveCallbackGroup`。tf2 的 listener 本來就把兩個訂閱放在
`ReentrantCallbackGroup`（原始碼註解寫得很清楚就是為了這件事），
配上多執行緒之後，等待期間 TF 照樣收得進來。

實測差別：不等 → 57% 的幀失敗（而且訊息說只差 **8 毫秒**）；
多執行緒 + 等 50 ms → **100% 成功**，約 14.5 Hz。

**② `spin_thread=True` 不能配「自己的 node」用。**
看原始碼（`tf2_ros/transform_listener.py` 的 `run_func`）：它會把傳進去的 node
**再 `add_node` 進第二個執行器**。而 `rclpy.spin(node)` 已經把同一個 node 放在
另一個執行器裡了 —— 一個 node 不能同時在兩個執行器，TF 回呼會停擺。
要用它的話必須傳 `node=None`，讓它自己建一個專用 node。

```bash
    search_x: [5.6, 5.6, 0.0, 0.0], search_y: [-9.0, 9.0, 9.0, -9.0]}"
```

| 欄位 | 地面車的語意 |
|---|---|
| `distance` | 站位距離。**0 = 用參數 `track_standoff_m`（預設 3 m）** |
| `altitude` | **忽略**（沒有高度這個概念）。給非零值會印一行說它被忽略 |
| `duration` | 追多久。時間到算**成功**，不是逾時 |
| `search_x/y` | 看不到目標時要巡的環線（map 座標）。空的 = 原地等 |

### 跟隨直接送速度，搜尋才走 Nav2（2026-11-15 改）

**2026-11-14 那版**是跟隨時每次算一個「站位點」送 `NavigateToPose`。
量出來的問題：真正在追的時候平均只有 **0.60 m/s**（目標 0.5、車體上限 1.0），
149 秒跟丟 7 次。原因算得出來：站位點只在前方約 1.1 m，Nav2 是「開到那個點
然後停」，用 `acc_lim_x 1.0`／`decel_lim_x -1.5` 跑 1.1 m 要 1.93 秒，
平均 0.57 m/s，和實測吻合。

🔑 **無人機 2026-10-16 已經走過同一條路**（`drone_api_node.py` 的
`DO_REPOSITION` → 速度控制）：那邊試過拉高更新率、縮小容差、調加速度限制，
**完全沒有改善**，結論是「問題不在調參，而在用位置設定點追移動目標這個架構」。
所以不要再試「把站位點拉遠一點」這類調整。

現在的分工和無人機一致：

| 階段 | 怎麼動 | 為什麼 |
|---|---|---|
| 跟隨 | `husky_api_node` 自己 10 Hz 發 `cmd_vel` | 目標在動，要連續追 |
| 搜尋 | Nav2（`NavigateToPose` 一個一個航點） | 「開到航點」本來就該用位置控制，而且有 costmap |

當初選 Nav2 的三個理由，現在各自怎麼處理：

| 當初的理由 | 現在 |
|---|---|
| 倉庫有貨架，自己發 `cmd_vel` 沒有避障 | 照抄無人機的禁飛方框擋牆（見下面「擋牆」）。⚠️ 只擋得住地圖上畫的貨架和牆 |
| 滑移轉向不能側移，要先轉頭 | 控制律本身就是「方位誤差 → ω、距離誤差 → v，誤差大時先轉頭」 |
| 不用搶 `cmd_vel` | 接手前先取消 Nav2 目標，回到搜尋時放手（`_release_velocity`） |

控制律是 `follow_cmd`（純函式，`t_track_geometry.py` ⑪~⑯ 釘住正負號）：
`kp_lin` 是 **2.0 不是 0.8** —— 比例控制要「落後到 kp × 誤差 = 目標速度」
才跟得住，0.8 時要落後 0.625 m，實測就是一路被拉開。

追蹤還是「**一個任務、很多個 Nav2 目標**」（搜尋那段），所以 Nav2 的回呼
要分流：子目標完成**不能**結束整個追蹤任務，否則積木的 `task.seq` 會在半路
跳成 `done`，「等待完成」會以為追蹤做完了。見 `_on_result` 的註解。

### 三個階段

| 階段 | 什麼時候 | 做什麼 |
|---|---|---|
| 跟隨 | 目標位置 < `track_fresh_s`（1.5 秒） | 直接送速度 |
| 跟隨（等） | 1.5 ~ `track_search_after_s`（5 秒） | **繼續朝最後看到的位置開**，不要急著掉頭 |
| 搜尋 | > 5 秒沒看到 | 依序走搜尋環線（Nav2） |

⚠️ **中間那段是刻意的。** 目標靠太近（< 2 m）時偵測率會掉，但它其實就在
眼前。只有一個門檻的話，車會在目標就在正前方的時候掉頭跑去搜尋。

⚠️ 中間那段 2026-11-15 之前是「原地停住」—— 偵測每閃一下車就停死、看到了
再衝到滿速，就是「頓一下頓一下」。改成繼續朝最後看到的位置開：那個位置
只有一兩秒舊，車愈近速度自然愈小。

搜尋環線**和目標反向**（對頭相遇最快：47 m 的環線反向最久 19 秒，同向 31 秒）。
目標**轉過路口**的那一刻（目標落在環線的下一段）才把繞行方向翻成同向，
而且只翻一次 —— 見 `_check_corner`。

### ~~兩道重送閘~~（2026-11-15 起沒有作用）

Nav2 站位點那版的設計：站位點移動超過 `track_goal_move_m`（0.5 m）**而且**
距離上次給目標超過 `track_goal_interval_s`（2 秒），才重新給 Nav2 目標。
跟隨改成直接送速度之後就沒有東西可擋了，這兩個參數現在只剩宣告。

### 太近就倒車，車頭照樣對著目標

距離小於「站位 − 死區」（3.0 − 0.3 = 2.7 m）時，控制律直接給**負的 v**，
ω 照樣把車頭對著目標 —— 相機一直看得到它。倒車上限是 `track_backup_speed`
（0.7 m/s，比倉庫目標車的 0.5 快，守得住距離）。

（Nav2 站位點那版**不能**這樣做：站位點跑到車後面時，Nav2 會把車掉頭開過去，
而終點朝向不被檢查，車會變成背對目標。所以那版只在太遠時才動，太近要另外
發 `BackUp`。）

### 實際停的距離會比站位距離大一點

兩個已知的加項，都不是誤差：

- **深度的 0.28 m 偏移**（量到車尾表面，見 H7）
- **速度控制的死區 `track_speed_deadband_m`（0.3 m）** —— 誤差在這以內就不動，
  免得一直來回修

（Nav2 站位點那版還要再加 `xy_goal_tolerance` 0.40 m，所以下面 2026-11-14 的
驗收數據停在 3.38 m。）

### 對頭相遇：倒車退過路口，停在外側讓路（2026-11-15）

搜尋是反向繞的，所以第一次碰到目標一定是**對頭**。這時不能原地轉 180°
（會變成車在目標前面、目標朝車尾開過來），也不能「倒進下一段環線」
（目標轉彎後又朝車開過來，車永遠在它前面）。

單線道上要讓目標從前面變到後面，只能讓它從車旁邊過去，而唯一不在它路上
的地方就是**路口往外延伸的那一小段**：

```
        北牆 y=12（加大後 11.2）
            [車]   ← 車中心停在約 y=10.5，車頭 y=10.0
      ──────●──────── y=9 路口：目標在這裡轉彎（車頭最遠到 y≈9.3），從車前面過
            │
            ▲ 目標（對頭開過來）
```

做法是限制倒車時車中心不能離開「搜尋環線外接矩形 + `track_pocket_m`（1.8 m）」，
前瞻 0.3 秒。四個路口外側到牆都有 3 m，實際停的位置還會被牆再擋一次。
節點啟動時會檢查 `track_pocket_m` ≥ 1.2，太小會印警告。

⚠️ 2026-11-15 下午那版是「退到環線邊界就停」，但它檢查的是**車後方 1.4 m
那個點**，結果車中心停在**路口前 0.6 m**（實測 y=8.55，路口 y=9）——
剛好擋在目標的路上。目標車沒有碰撞箱，於是直接穿過去，看起來像
「沒有換成順向追的機制」。

### 擋牆（2026-11-15，照抄無人機的禁飛方框）

跟隨不走 Nav2，就沒有 costmap。擋牆用的是 `warehouse_geometry.yaml` 的
`no_fly_boxes`（四排貨架 ＋ 四面外牆），作法照抄 `drone_api_node.py` 的
`_box_entry_axis`／`_clamp_no_fly`：

1. 方框往外加大 `track_wall_margin_m`（0.8 m，和無人機一樣）
2. 先算「想往哪走」的世界座標速度，預判 1 秒，**只砍朝牆那一面的分量** ——
   剩下的就是沿著牆面滑行，不會一靠近貨架就整個停住
3. 再換成差速車的 v、ω：車頭轉向夾完的方向，v = 速率 × cos(車頭誤差)
4. 最後用**實際的車頭方向**再檢查一次（車頭可能還沒轉過來）

🔴 **差速車和無人機真正不一樣的地方：車身是長方形，原地轉頭會掃到東西。**
無人機在這方面是圓的。實測過一次：車中心離貨架角 0.52 m 時原地轉了 26°，
車尾掃上貨架角。所以依車中心離貨架/牆的距離分三層：

| 車中心離貨架/牆 | 行為 |
|---|---|
| > 0.8 m | 沿牆滑行（車頭方向可以帶一點往裡的分量）|
| 0.65 ~ 0.8 m | 可以轉頭；移動**不准往牆的方向**（車頭差 10° 以內才准走）|
| < 0.65 m | **不准轉頭**，先沿車身方向直直移開 |

0.65 = 車身外接半徑 √(0.495² + 0.335²) = 0.598 ＋ 0.05。

⚠️ 中間那層不能設成「完全不准有往裡的分量」：車頭靠 ω = kp × 誤差轉過去，
誤差是**漸近**收斂的，永遠停在 +0.01° 這種值，結果永遠 v=0、卡死在貨架角旁。
單元測試踩到過，所以用「車頭差 10° 以內」。

⚠️ 舊的擋牆（2026-11-15 下午以前）只檢查車中心線前方 1 秒的**一個點**、
方框沒有加上車身大小、擋到時只把 v 歸零而車頭還對著貨架後面的目標 ——
轉彎時幾乎每次都撞。

⚠️ 這**不是**避障。目標車、無人機、臨時放的東西都不在方框裡。

### 跟隨不再頓、沿足跡過轉角（2026-11-16）

Oliver 回報三件事：①「跟隨中」和「已就位」一直來回跳 ②一到轉角車就轉到
快撞牆、一直調整，然後目標不見 ③不見之後沒去它最後出現的位置，而是去上個
經過的轉角。

**① 不只是文字在跳，車真的在頓。** 舊的不動區邊緣是跳的：距離誤差 < 0.3 m
就給 0，≥ 0.3 m 就給 `2.0 × 誤差` = 0.6 m/s。目標走 0.5 m/s 時，跟上它只需要
落後 0.25 m —— 落在不動區裡，於是「停 → 被拉開 → 衝 → 又停」。改成出了不動區
從 0 連續往上長（`dist_speed`），代價是跟移動目標時車會多落後 0.3 m（停在約
3.5 m）。訊息另外加 1 秒防抖（`hold_kind`），擋牆類的安全訊息不延後。

**② 直線追會切過貨架角。** 跟隨一直是「朝目標現在的位置直線開」，目標一轉彎
那條線就穿過貨架角，擋牆只能讓車貼著貨架滑，車頭被帶偏，相機就看不到了。
改成把目標看過的位置平滑後記成一條**足跡**（每 0.3 m 一點、最多 25 m），車在
足跡上時瞄「足跡上前方 1.5 m 的點」、距離沿路量（`trail_plan`）。目標走過的地方
一定能通行，所以不用事先知道環線長怎樣。剛找到目標、對頭相遇、太近要倒車
這三種情況車不在足跡上（或在尾巴前面），照舊用直線追。

**③ 跟丟後的順序改成：**

1. 車在足跡上 → 沿足跡開到目標最後出現的位置（`_track_chase`），到了轉向它
   離開的方向看。轉角處通常一轉過去就看到了
2. 還是沒看到 → **直接**上搜尋環線，不做轉圈/倒車（車已經在最後位置看過了）
3. 起點用「目標最後的移動方向」挑那一段，而且**順著它的方向**繞
   （`leg_and_dir`）。舊的是取最近的一段＋還沒翻向時的反向繞，在轉角跟丟
   就會被派回剛經過的那個轉角

車不在足跡上（對頭相遇時）跟丟的話，還是原本的「原地等 → 轉圈/倒車 → 搜尋」。

### 擋牆改成 CBF 安全濾波（2026-11-17）

原本的擋牆是三層手寫規則，每一層都是為了補一個實測出來的洞：
「預看 1 秒會穿進方框就砍掉那一軸」（沿牆滑）、「中心 0.65 m 內不准轉頭」
（車尾會掃到）、「不准退出路口外側範圍」（讓路）。層與層之間的互動要一條一條推。
改成 CBF（Control Barrier Function）之後，全部用同一條式子處理：

    h ≥ 0 代表安全（例：h = 離貨架的距離 − 0.8 m），要求 ḣ ≥ −α·h
    ＝「往邊界靠近的速度，不准超過 α × 離邊界還有多遠」→ 越近越慢、剛好停在邊界上

然後在所有限制都滿足的指令裡，挑**離控制律原本想要的那組最近的**。什麼都沒擋到
時原封不動，平常跟隨的手感不變。只有一條限制起作用時，修正量只在違規的方向上，
和它垂直的分量（null space）不動 —— 這就是「沿牆滑」。

**流程（`_follow_world_cbf`）：**

```
沿足跡跟 / P 控制 → ① 想往哪走（世界座標速度）
                  → ② 第一層 CBF（cbf_world）：砍掉往貨架的分量 → 沿牆滑的方向
                  → ③ 車頭轉向②的方向，換成 (v, ω)
                  → ④ 第二層 CBF（cbf_filter）：用實際車頭方向把關 v，保證不撞
                  → cmd_vel → 看門狗 → 輪子
```

限制有三種：貨架與牆、讓路範圍（已經在外面時只是不准更外面）、不撞目標車
（1.5 m，只防碰撞；排最後，衝突時先讓）。只有兩個變數，求解就是「把點投影到
凸多邊形上」：列舉「點本身／投影到每條邊／每兩條邊的交點」，挑可行裡最近的
（`qp_project`），不用裝求解器。每次約 0.02 ms。

#### 規劃時沒想到、實測才改的三件事

1. **車身用一個大圓（半徑 0.6 m＝外接圓），不是前後兩個小圓。** 兩個小圓能讓 ω
   出現在限制裡（濾波器可以選擇「轉開」），但有一個一定會掉進去的陷阱：車和
   貨架平行、兩個圓同時貼著邊界時，往哪邊轉都會讓其中一個圓靠近貨架，最後只能
   停住（離線㉔：卡 9 秒、跟丟）。大圓裡車怎麼轉都安全，轉頭不需要被限制。
   兩種都留在程式裡（`CBF_BODY`）。
2. **分兩層，而且第一層多留 0.15 m。** 只有第④層時，目標在貨架角另一邊，車頭對著
   貨架就停住、不會自己轉開（離線⑳：卡 16 秒）—— 要第②層決定「往哪走才過得去」。
   兩層邊界一樣時，車沿著邊界滑、h 趨近 0，車頭偏 0.3° 就停（⑳：卡 6.7 秒），

### 轉角提早轉頭：目標留在畫面內（2026-11-17，C4）

Oliver 回報：轉彎時目標已經離開畫面一下子了，車才轉過去。

**原因可以算出來。** 車沿足跡跟、瞄準足跡上前方 1.5 m 的點，車頭（＝相機，±35°）
照著路走。0.5 m/s 過 90° 轉角、車在後面 3.5 m：目標過轉角後約 **2.9 秒**就偏到
35° 出畫面，而瞄準點要到第 **4 秒**才轉過轉角，車才開始轉。車頭同時負責「往哪開」
和「看哪裡」，轉角處兩者分開，原本是「開」優先。

**做法：在 CBF 加一條視野限制**（`fov_constraint`），β＝目標在車頭的方位：

    h = cos β − cos 25°          （25°：比相機邊緣 35° 留 10° 餘裕，快到邊緣就開始轉）
    ḣ =  sin β · ω                               車轉頭：直接把 β 拉回來
       + sin β ·(rx·sinθ − ry·cosθ)/r² · v      車往前開：目標偏在旁邊時越開越偏
       − sin β ·(r × 目標速度)/r²                目標自己橫著走（轉角就是這個）

第三項要目標速度：平滑後的位置差分再平滑一次（`vel_update`，0.5 秒）。沒有它的話
限制只會在目標已經偏出去後才反應，提早不了。推導用數值微分驗過（測試㊴，300 個
隨機情境全部吻合）。

**優先順序：** 貨架／牆／讓路範圍（硬）＞ 不撞目標 ＞ 目標留在畫面內。解不出來時
從最軟的開始放掉 —— 貨架真的擋住時，寧可讓目標暫時出畫面也不會撞。只在剛看到
目標（1.5 秒內）、而且目標在 ±90° 以內時啟用；跟丟後沿足跡開、搜尋時都不用。
為了看目標而轉頭不算擋牆，不會出現「沿著貨架或牆走」的訊息。

#### 近距離跟丟的處理（2026-11-14 加的）

原本的症狀：目標會**自己朝車開過來**，靠到 1.2 m 時偵測就掉了，車撐 5 秒之後
回去跑搜尋環線 —— 而目標可能就在正前方 1 公尺。站位 3 m 擋不住這件事。

兩段處理：

**① 先擋：太近就直線倒車**

2026-11-15 起由速度控制直接倒車（見上面「太近就倒車」）。
2026-11-14 那版是：靠得比 `track_min_m`（2.5 m）近時，用 Nav2 的 **`BackUp`
行為**退回站位距離。`BackUp` 現在只剩②重找時用，它的特性還是重要：

🔑 關鍵是 **`BackUp` 不轉向**。實測（2026-11-14）：

| 動作 | 要求 | 實測 |
|---|---|---|
| `BackUp` `target.x=+1.0` | — | 沿車頭方向 **−1.027 m**、車頭變化 **0.0°** |
| `Spin` `target_yaw=+1.5708` | +90° | 轉了 +94.9°，原地漂移 0.26 m |

所以 `target.x` 給**正值**就是往後退，而且退完車頭還是對著目標。這和「送一個
在車後面的導航目標」完全不同 —— 那個會讓規劃器把車掉頭開過去，而終點朝向
不被檢查（`yaw_goal_tolerance` 是 3.14），結果是背對目標。

**② 真的跟丟了：轉圈 → 倒車 → 才跑搜尋環線**

只有「最後看到時 < `track_close_m`」才做。兩步解決不同的幾何：

| 步驟 | 解決什麼 |
|---|---|
| 轉一圈 | 目標從旁邊開走或開到車後面 —— 前視相機永遠看不到那裡 |
| 後退 | 目標停在正前方 1 m 不動 —— 每個角度都太近，轉圈沒用 |

先轉再退，因為原地轉比盲退安全。兩步都試完之後隔 20 秒會再試一輪
（目標可能悄悄繞到旁邊）。

#### 驗收數據

**④ 目標朝車開過來**（0.3 m/s，從 +4.72 一路開到 −12.39，共 17 m）

| | 修之前 | 修之後 |
|---|---|---|
| 相距 | 1.93 → **0.9 m**（一路被壓縮）| 穩在 **2.45~2.67 m** |
| 跟丟 | 有，之後回搜尋環線 | **57 筆取樣全部是「跟隨」，一次都沒跟丟** |
| 車 | 被逼到西牆退不動 | 退了 15.5 m 一路跟著 |

#### 🔴 還是會失敗的兩種情況

1. **沒有退路**：車被逼到牆邊就退不動了（實測過，車停在 x≈−17.2 的西牆前，
   目標在 1.02 m 處看不到）。這時 `BackUp` 會被 Nav2 拒絕，重找的第二步直接
   跳過。這是幾何上的死局，只能等目標自己走開。
   在搜尋環線上對頭相遇時，現在會退到路口外側讓路（見上面），不會被逼到牆邊；
   這條指的是沒給環線、或在環線以外的地方被逼退。
2. **目標比倒車快**：`track_backup_speed` 預設 0.7 m/s（2026-11-14 是 0.4，
   當時 Oliver 實際看到目標開得比倒退快）。目標更快的話追不上，距離會持續縮小。

#### ⚠️ `track_close_m` 必須大於車維持的距離

`track_close_m` 要大於 `max(track_min_m, track_standoff_m + track_arrive_tol_m)`，
不然**整段重找是死的** —— 車維持在 2.5 m，而門檻也是 2.5 的話，跟丟時
`last_dist` 剛好不小於門檻，永遠不會觸發（2026-11-14 實際踩到，而且沒有
任何症狀，只是「重找好像從來沒作用過」）。節點啟動時會檢查這個關係並印警告。

⚠️ 看 `watch_track.py` 的輸出時注意：**搜尋階段的「目標」和「相距」是
最後一次看到的位置**，不是當下的。車開過那個舊位置時「相距」會變得很小，
那不是真的靠近目標 —— 看「舊」幾秒就知道。

### 部署時踩到的四個雷（都已修掉並留下防線）

1. **`merge_flows.py` 的標記寫死 `generated-by: drone_nodered`** —— 拿地面車的
   流程單獨合併會把無人機的 14 個分頁與積木整批刪掉。改成 regex 認得任何
   `<套件>_nodered`。
2. **積木同名** —— 地面車的「導航到座標」和無人機同名，而 merge 有「名稱相同
   就當成同一個」的比對。改名成「車：…」。

4. **服務層要常駐，不能跟著場景走** —— `husky_api_node` 原本放在場景的 launch，

5. **被拒絕的理由要進狀態** —— 服務回 `success=false` 時只回給呼叫端的話，

## 兩台同場時 Nav2 的啟動順序（2026-11-15 改成等事件）

兩套 Nav2 **不能同時 configure** —— 後起的那套會卡在「Configuring map_server」，
而且卡住之後不會自己重試，要整個重開。

原本的解法是「地面車的 Nav2 固定延後 35 秒」。但實測每套 Nav2 從啟動到就緒
**只要 3~4 秒**，那 35 秒裡有 31 秒是純浪費的 —— 而且還是用猜的，機器更忙的
時候反而可能不夠。

現在改成等事件：`both_all.launch.py` 傳 `wait_for_action:=/navigate_to_pose`，
地面車這邊跑 `scripts/wait_for_action.py` 等那個 action server 出現，再等
`nav2_settle`（預設 5 秒）才開自己的 Nav2。

⚠️ **為什麼看到 action 之後還要再等 5 秒**：Nav2 的 action server 是在
**on_configure** 就建立的，不是 on_activate。看得到只代表對方 configure 完了，
可能還在 activate（實測約 2 秒）。

⚠️ **等不到也要放行**（`nav2_wait_timeout`，預設 120 秒）：對方沒起來時本來就
沒有搶 configure 的問題，卡在那裡只會讓地面車永遠不動。

單獨跑地面車時不傳 `wait_for_action`，維持原本的 `nav2_delay` 計時器。

## 車體幾何的唯一來源

原廠模型自己帶的數字，**不要去查別的規格表**：

```
輪距 0.5709 m    輪半徑 0.17775 m    車體約 0.99 x 0.67 m
模型原點離地 0.14275 m（輪心 0.035 + 輪半徑）
速度上限 1.0 m/s   扭力 35 N·m
```

這些值有四個消費者（DiffDrive、輪子的 collision、`warehouse_geometry.yaml`、
世界檔的 pose z），`test/t_husky_model.py` 會把它們綁在一起檢查。

## 三個雷

1. **DiffDrive 的 `<topic>` 是絕對路徑**，不會自動加 model 的 namespace。
   只寫 `cmd_vel` 會開在全域 `/cmd_vel`，bridge 等在 `/model/husky/...`
   會完全收不到訊息 —— 而且話題宣告得出來，所以很難查。
2. **gz 的 DiffDrive 沒有指令逾時**：送過一筆 `cmd_vel` 之後，沒人再送它也會
   永遠沿用最後那一筆，車子會一路開到撞牆、輪子在牆邊空轉。所以 Nav2 和
   bridge 中間一定要有 `scripts/cmd_vel_watchdog.py`（0.5 秒沒指令就送零），
   對應無人機那邊 `cmd_vel_to_px4_node` 的 `cmd_timeout_s`。

3. **四輪滑移轉向，輪式 odom 的轉角會灌水 46%**：實測下 0.5 rad/s，
   真值只轉到 0.69 倍，odom 卻報 1.44 倍。所以
   ① DiffDrive 用「等效輪距」0.834（＝實際 0.5709 × 1.46），達成率 0.69 → 0.98
   ② 定位改用 OdometryPublisher 的**真值**里程計，輪式那份改名 `odom_wheel` 留著比較
   ③ 真值里程計報的是**世界座標**，所以 `map → odom` 是單位變換，不是 spawn 偏移
   實機要用的話這三點都不成立，必須換成 AMCL 或輪式＋IMU 的 EKF。

4. **世界檔是產生出來的**，見 `gz/worlds/README.md`。跑 `gen_warehouse.py`
   記得加 `--target hatchback`。

## 模型出處

`gz/models/husky/` 來自 Gazebo Fuel 的
[Clearpath Robotics Husky A200](https://app.gazebosim.org/OpenRobotics/fuel/models/Clearpath%20Robotics%20Husky%20A200)
（OpenRobotics 發布，CC0 1.0）。改了四處，都記在 `model.sdf` 的檔頭。

原廠包提供的是 mesh／collision／inertial／joint 與輪距輪徑 —— **車體幾何和外觀**。
原廠帶的驅動是 Gazebo-classic 的 ROS 1 外掛（`libhusky_gazebo_plugins.so`），
Harmonic 載不動，所以換成 gz-sim 內建的 `DiffDrive`；`OdometryPublisher` 原廠
根本沒有，是另外加的。所以「會動」和「知道自己在哪」都不是模型自帶的功能。
